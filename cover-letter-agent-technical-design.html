Cover Letter Agent

A Planner → Generator → Reviewer pipeline that turns a job posting into a formatted, template-conformant cover letter draft — no manual chat loop, no context bloat from dumping every past letter into one prompt.

Replaces a manual Claude Project workflow (paste JD → copy output → format → upload) with a repeatable local CLI: retrieval-based example selection, a fixed/flexible template contract, and a rubric-checking Reviewer agent that catches what a single generation pass misses.

Problem

Executive Summary

Cover letters are currently generated through a manual chat loop: paste a job description into a Claude Project pre-loaded with an instructions file and ~15 past letters as implicit examples, then manually copy the output into a .docx and upload it to Drive. This works, but it doesn't scale cleanly and has no verification step before the draft reaches you.

Why this matters

Three specific gaps motivate the pipeline design: context bloat (all past letters sit in context regardless of relevance to the current role), no verification step (nothing checks that fixed sentences survived unmodified or that names are correct), and no repeatability (every letter requires a fresh chat and manual formatting).

Goals & Non-Goals

Goals

  • Given a job posting URL or pasted text, produce a .docx draft following the fixed/flexible template.
  • Select few-shot examples by relevance to the target role, not by dumping the whole bank into context.
  • Verify the draft against a rubric before returning it, with one self-correction retry.
  • Run as a local CLI tool with no external write dependencies.

Non-Goals

  • No Drive upload — removed to avoid Cornell OAuth friction; output stays local.
  • No web UI in v1.
  • No multi-user support — this is a personal tool.
  • No fine-tuning; all behavior is prompt- and retrieval-driven.
Structure

System Architecture

The pipeline follows a Planner → Generator → Reviewer pattern, with each agent scoped to a single, verifiable responsibility rather than one large prompt handling everything.

End-to-End Flow

1
Ingest
Fetch and parse the job posting from a URL (title, company, requirements), or accept pasted JD text as a fallback since scraping reliability varies by job board.
2
Retrieval
Embed the parsed JD and retrieve the top 2–3 most similar past letters from the cached embedding store, filtered by role type.
3
Planner
Classifies role type (quant trading / SWE / markets / trade support) and extracts structured JD fields — company, role title, key requirements.
4
Generator
Drafts the letter — fixed template sentences inserted verbatim, flexible sections written to match the target role using retrieved examples as style reference.
5
Reviewer
Checks the draft against a rubric — fixed sentences intact, correct company/role name throughout, length in range, no generic filler. Fails send one retry back to the Generator with specific issues.
6
docx Writer
Formats the approved draft into .docx and saves it to output/{company}_{role}.docx — no upload, ready for manual review.
The Agents

Components

Component File Responsibility
Ingest ingest.py Fetches JD URL, extracts posting text; falls back to pasted text since scraping reliability varies across Greenhouse, Lever, Workday, etc.
Retrieval retrieval.py Embeds all past letters once (cached locally), retrieves top-k nearest by cosine similarity at generation time. The main technical depth in the project.
Planner agents/planner.py Single API call. Input: parsed JD + instructions.md. Output: role classification, structured JD fields, retrieval request.
Generator agents/generator.py Single API call. Drafts the letter using instructions.md, retrieved examples, and Planner output.
Reviewer agents/reviewer.py Rubric checker, not a rewriter. Pass/fail + specific issues, capped at one retry to the Generator.
docx Writer docx_writer.py Formats the final draft into .docx matching existing letter-bank conventions.
Orchestrator orchestrator.py / main.py CLI entrypoint. Wires the full pipeline: python main.py <job_url>.

Key Design Decisions

Decision Rationale
Retrieval-based example selection over full-context injection Scales as the example bank grows; keeps the Generator's context focused on relevant style patterns instead of diluted across 15+ letters.
Separate Reviewer agent rather than generate-and-hope Catches deterministic failures — wrong company name, dropped fixed sentence — that a single-pass generation is prone to, without a human catching it manually.
One retry cap on Reviewer failure Avoids runaway loops and unnecessary API spend; two failures surface to the user instead of looping silently.
No Drive upload Removes an OAuth/API surface causing friction under Cornell's settings; local .docx output is simpler and more reliable for v1.
CLI-first, no UI Fastest path to a working, testable tool. A Chrome extension or other client can wrap this backend later without touching the core pipeline.

Open Questions / Future Work

  • Example bank growth — as more letters accumulate, does role classification need to get more granular (e.g. market-making vs. prop trading within "quant trading")? future
  • Feedback loop — track which letters led to interviews/responses and feed that signal back into example selection or Reviewer rubric weighting. future
  • Chrome extension wrapper — once the CLI backend is stable, wrap it in a FastAPI service (reusing the Gmail AI Reply Reviewer's backend pattern) for one-click generation from a job posting tab. future
